# 公路边坡风险知识图谱与风险研判 Agent 设计方案

> 文档状态：讨论稿  
> 版本：v0.2  
> 日期：2026-07-10  
> 适用范围：公路边坡基础档案、工程地质资料、巡检养护、监测分析、风险研判

## 1. 编制背景

当前项目已经以 G209 K2388+976～K2435+900 路段的工程地质勘察报告和施工图设计文件为样例，初步形成了灾害点、桩号、地层岩性、结构面、稳定性、防护措施、图纸和文档之间的关联图谱。

下面进一步要：

1. 图谱验收应先明确边坡全部属性字段，包括位置、岩土分类、灾害性质、地形地貌、地层岩性、结构、水文、气象、地震、防护、灾害历史、养护历史和稳定性分析等。
2. 后续希望建设能够依据知识图谱属性判断边坡风险的 Agent。
3. 图谱的业务中心应由“灾害点”调整为“边坡”。

与此同时，交通部研究院提供的《边坡属性表》及其批注已经被整理为 `slope_attribute_data_dictionary.json`。该数据字典对字段名称、数据类型、枚举值和部分填报约束进行了初步规范，但仍需从“填报表结构”进一步转化为“可计算、可追溯、可支持风险研判的图谱结构”。

本方案的目标不是单纯将属性表绘制成树，而是设计一套可以持续接入工程资料、巡检记录、监测数据和规范规则的底层知识模型，并为风险研判 Agent 提供结构化、时序化、有证据的数据基础。

## 2. 设计结论

本项目建议采用以下总体方案：

> 以 `Slope（边坡）` 为核心业务实体，以工程空间、地质环境、变形灾害、防护养护、监测分析、暴露后果、规范规则和证据来源构成相互关联的子图；简单稳定信息作为边坡属性，复合对象建成实体，动态信息建成事件或观测记录，风险结论建成可版本化的评估记录。

需要特别明确：

- “边坡是核心实体”不等于整个图谱必须是一棵以边坡为根的树。
- “属性字段”是业务采集要求，不等于每个字段都要建成图节点。
- “存在防护工程”不等于防护工程当前有效。
- “未填写裂缝”不等于“无裂缝”。
- “稳定性状态”不等于“综合风险等级”。
- “灾害点”“灾害体”“灾害事件”“潜在灾害类型”不能混为同一个概念。
- Agent 不应直接依靠大模型主观判断工程风险，应以图谱事实、规范规则、专业模型和人工审核为依据。

## 3. 建设目标与边界

### 3.1 建设目标

图谱应支持以下业务能力：

1. 形成“一坡一档”的边坡基础档案。
2. 将勘察、设计、图纸、巡检、养护、监测和规范资料关联到同一边坡。
3. 保留数据的来源、时间、适用工况、置信度和审核状态。
4. 支持按路线、桩号、岩性、结构、病害、防护、风险等级等条件查询。
5. 支持追踪边坡随时间发生的变形、灾害、治理和风险变化。
6. 支持风险 Agent 检查数据完整性、识别潜在灾害模式、调用规则和模型、生成可解释的风险评估。

### 3.2 当前阶段不宜承诺的能力

仅凭两份 G209 设计期 PDF，当前不能可靠实现：

- 实时风险预警；
- 基于大量历史样本训练的可靠概率预测模型；
- 对所有图纸图元、遥感影像和三维点云的全自动理解；
- 无人工复核的安全关键决策；
- 对缺失的地下水、降雨、养护和监测数据进行推测补全。

当前阶段可实现的是“历史资料基线图谱 + 规则驱动的场景化风险研判原型”。实时风险能力需要继续接入巡检、养护、监测、交通和气象数据。

## 4. 数据来源分层

数据来源建议分为四类，分别承担不同职责。

| 数据层 | 典型来源 | 主要作用 |
| --- | --- | --- |
| 工程实例资料 | 勘察报告、施工图、竣工资料、巡检记录、养护记录、监测数据 | 描述具体边坡当前和历史状态 |
| 环境与业务数据 | 气象、地震、水文、交通量、周边人员与设施 | 补充触发因素、暴露程度和后果 |
| 标准规范知识 | 国标、行标、地方标准、技术指南 | 提供术语、分类、阈值、评价流程和规则依据 |
| Schema 与管理要求 | 交通部研究院属性表、批注、数据标准、专业意见 | 决定采集哪些信息以及如何治理数据 |

G209 两份 PDF 是当前图谱主要的工程实例资料。规范文件不是具体边坡属性的主要来源，而是风险判断规则和设计依据的来源。

## 5. 核心建模原则

### 5.1 判断“属性还是节点”的规则

一个数据项是否建成节点，至少判断以下问题：

1. 是否具有独立身份？
2. 是否可能出现多条记录？
3. 是否随时间、位置或工况变化？
4. 是否具有自己的属性？
5. 是否需要与边坡之外的其他对象建立关系？
6. 是否需要单独记录来源、审核或生命周期？

如果以上答案均为否，通常应作为边坡属性；如果有一项或多项为是，应优先建成实体、事件、观测或分析记录。

例如：

| 数据项 | 建模方式 | 原因 |
| --- | --- | --- |
| 边坡编号 | 边坡属性 | 单值、稳定、无独立关系 |
| 坡高、坡长、坡度 | 边坡属性 | 适合直接计算和筛选 |
| 岩性 | 实体或受控分类 | 可被多个边坡共享，可连接性质和规则 |
| 结构面 | 实体 | 多组结构面，每组有产状、间距、延伸等属性 |
| 地下水位 | 时序观测 | 随时间和位置变化 |
| 裂缝 | 变形观测 | 可多条、可扩展、需要追踪变化 |
| 防护工程 | 工程设施实体 | 有位置、参数、建成时间和当前状态 |
| 灾害历史 | 灾害事件 | 具有时间、规模、损失和处置过程 |
| 稳定性分析 | 分析记录 | 与方法、参数、工况、时间和规范相关 |
| 风险等级 | 风险评估记录 | 会随时间和场景变化，必须保留历史 |

### 5.2 业务图与证据层分离

不应为了记录来源而把每个数值都显示成业务节点。例如“坡高 45 m”在业务图中仍然是 `Slope.height_m=45`。

但风险关键属性必须能追溯来源，因此底层增加 `PropertyAssertion（属性断言）` 或等价的证据映射表，记录：

```text
subject_id        = slope_g209_08
property_code     = slope_height_m
value             = 45
unit              = m
source_evidence   = evidence_xxx
valid_time        = 2021-06
confidence        = 0.92
review_status     = approved
```

关系同样可能存在来源、时间、置信度和争议。例如“降雨触发了某次滑坡”与“某次滑坡发生前存在降雨”不是同等强度的结论。风险关键关系应采用以下两种方式之一保存证据：

1. 在关系上保存 `evidence_id`、`confidence`、`review_status` 等属性；
2. 将关系提升为 `RelationshipAssertion（关系断言）`，明确主语、谓词、宾语、来源和审核状态。

证据断言层用于数据治理和风险解释，默认不必在前端全图中展开。这样既能保持业务图清晰，也能做到属性级和关系级追溯。

### 5.3 实例知识与分类知识分离

图谱至少区分：

- 实例：某一具体边坡、某一条裂缝、某一次养护。
- 分类：岩质边坡、砂质页岩、滑坡、崩塌、主动防护网等类型。
- 规则：何种条件触发何种风险判断。

“属性类别”“基本信息”“水文”“气象”等页面栏目不应作为领域实体。它们可以作为前端菜单或数据字典分组，不进入实例图谱主干。

### 5.4 时间必须显式表达

动态记录至少需要两个时间概念：

- `observed_at/occurred_at`：现场观测或事件实际发生时间。
- `recorded_at`：数据进入系统的时间。

需要时再增加：

- `valid_from/valid_to`：结论或数据的有效期。
- `analysis_time`：分析计算时间。
- `assessment_time`：风险评估时间。

仅保存“最近一次时间”会丢失历史，不满足趋势分析要求。

### 5.5 缺失、未知和否定必须区分

建议统一使用：

| 状态 | 含义 |
| --- | --- |
| `present` | 已确认存在 |
| `absent` | 已调查并确认不存在 |
| `unknown` | 没有足够信息判断 |
| `not_observed` | 已开展调查但本次未观察到 |
| `not_applicable` | 对该类型边坡不适用 |

数据库中的 `null` 只表示缺失，不能自动解释为 `false` 或安全状态。

## 6. 核心实体边界

### 6.1 Slope：边坡

`Slope` 表示现实中持续存在、可以独立巡检、养护、监测和评估的一段公路边坡，是本图谱的核心业务实体。

边坡应具有系统稳定 ID。桩号、名称和业务编号都可能调整，不能直接作为数据库主键。建议：

```text
slope_id = 全局稳定 UUID 或组织统一编码
```

路线编号、起止桩号、侧别可以作为边坡匹配和去重的候选键，但不能替代稳定 ID。

### 6.2 HazardBody：灾害体或隐患体

`HazardBody` 表示边坡内部具有空间范围的危岩体、潜在滑体、堆积体等对象。一处边坡可能存在多个灾害体，一个灾害体也可能跨越人为划定的边坡段，因此两者不是简单等同关系。

### 6.3 HazardEvent：灾害事件

`HazardEvent` 表示某一时间实际发生的滑坡、崩塌、落石、泥石流、塌陷等事件，具有时间、规模、影响、损失和处置结果。

### 6.4 HazardType：灾害类型

`HazardType` 是受控分类词表，例如滑坡、崩塌、落石、泥石流。它不是灾害事件本身。

### 6.5 状态和类型不能混用

“不稳定边坡”更接近稳定性评价或状态，不宜与“崩塌”“滑坡”直接并列为同一种灾害类型。建议分别表达为：

```text
Slope ──HAS_STABILITY_STATUS──> 不稳定
Slope ──SUSCEPTIBLE_TO──> 滑坡
Slope ──CONTAINS_HAZARD_BODY──> 某潜在滑体
```

## 7. 边坡核心节点属性

边坡节点只保存边坡自身当前已发布的、相对稳定、单值、便于计算和检索的信息。边坡经过开挖、加固或灾后重塑后，坡高、坡度等也可能变化，因此根节点属性是“当前有效快照”，历史值仍通过属性断言、调查记录或版本保存。

### 7.1 身份与位置

| 字段 | 类型 | 建议要求 | 说明 |
| --- | --- | --- | --- |
| `slope_id` | string | 必填 | 系统稳定唯一标识 |
| `slope_code` | string | 条件必填 | 交通部研究院业务编号 |
| `slope_name` | string | 必填 | 业务名称 |
| `route_code_cache` | string | 必填 | 便捷检索缓存，正式归属由关系表达 |
| `start_station_raw` | string | 必填 | 原始起点桩号 |
| `end_station_raw` | string | 必填 | 原始止点桩号 |
| `start_station_m` | number | 必填 | 标准化累计里程 |
| `end_station_m` | number | 必填 | 标准化累计里程 |
| `side` | enum | 必填 | 左侧、右侧、中分带等 |
| `road_slope_relation` | enum | 待确认 | 当前属性表给出上行/下行，但字段含义需交通部研究院确认 |
| `geometry` | geometry | 条件必填 | 点、线或面几何 |
| `coordinate_crs` | string | 有坐标时必填 | 坐标参考系 |

坐标建议使用标准几何字段保存，并可缓存起止点 X、Y、Z。不能只保存坐标值而不保存 CRS。

### 7.2 基础几何与类型

| 字段 | 类型 | 建议要求 | 说明 |
| --- | --- | --- | --- |
| `slope_type` | enum | 必填 | 路堤、路堑等 |
| `material_nature` | enum | 必填 | 土质、岩质、土岩混合 |
| `slope_height_m` | number | 风险必填 | 坡高 |
| `slope_length_m` | number | 风险必填 | 需明确是坡面长度还是沿路线长度 |
| `slope_gradient_deg` | number | 风险必填 | 统一换算角度 |
| `slope_gradient_raw` | string/object | 建议保留 | 原文坡比、角度或百分比 |
| `slope_aspect_deg` | number | 建议新增 | 坡向，0～360° |
| `slope_structure_code` | enum | 岩质边坡风险必填 | 顺向、斜向、横向、逆向 |
| `bench_count` | integer | 可选 | 台阶级数 |
| `construction_year` | integer | 可选 | 建造年度 |
| `lifecycle_status` | enum | 必填 | 在役、治理中、封闭、废弃等 |

`engineering_geological_group_code` 可以作为受控分类代码保存在边坡节点中，同时通过关系连接正式的工程地质岩组分类节点。详细地层、岩性和结构面不得压缩成一个根节点字符串。

### 7.3 数据治理与当前状态缓存

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `current_technical_grade_cache` | enum | 最新技术状况等级缓存，不替代历史评定记录 |
| `current_risk_level_cache` | enum | 最新已发布风险等级缓存，不替代风险评估节点 |
| `data_completeness` | number | 0～1 或 0～100 的完整度 |
| `review_status` | enum | pending、approved、rejected |
| `data_version` | string | 当前发布版本 |
| `updated_at` | datetime | 最近更新时间 |

### 7.4 不放在边坡根节点中的内容

以下信息必须通过独立节点或记录表达：

- 地层、岩性、结构面和岩土参数；
- 灾害体、灾害类型和灾害历史；
- 裂缝、滑塌、隆起、渗水和设施损毁；
- 地下水位、降水、气温和冻融观测；
- 防护设施、排水设施和养护事件；
- 监测点、监测设备和监测值；
- 稳定性分析和技术状况评定；
- 风险评估、风险等级和处置建议；
- 图片、PDF、图纸和证据页；
- 填报人和填报时间。

`has_protection`、`has_disaster`、`has_maintenance`、`has_monitoring` 等布尔值建议由实际关系派生，不作为唯一事实来源。

## 8. 图谱节点体系

### 8.1 工程与空间组织

| 节点类型 | 关键属性 | 说明 |
| --- | --- | --- |
| `Project` | name、code、period | 工程项目 |
| `RouteSegment` | route_code、road_grade、station_range | 路线或路线段 |
| `AdministrativeArea` | province、city、county、code | 行政区划 |
| `Organization` | name、role、code | 建设、勘察、设计、施工、管养单位 |

### 8.2 地形地质

| 节点类型 | 关键属性 | 说明 |
| --- | --- | --- |
| `Geomorphology` | type、slope_form、valley_context | 地形地貌单元 |
| `Stratum` | code、name、geologic_age、thickness | 地层 |
| `Lithology` | name、weathering_degree、integrity | 岩性及状态 |
| `EngineeringGeologicalGroup` | code、name、properties | 交通部研究院给出的工程地质岩组分类 |
| `StructuralPlane` | dip_direction、dip_angle、spacing、extension、aperture、filling、persistence | 层面、节理、裂隙、软弱夹层等 |
| `RockSoilParameterSet` | unit_weight、cohesion、friction_angle、source | 岩土物理力学参数集 |
| `FailureMode` | type、description | 滑移、倾倒、坠落、圆弧滑动等破坏模式 |

### 8.3 水文、气象、地震与环境

| 节点类型 | 关键属性 | 说明 |
| --- | --- | --- |
| `HydrogeologicalCondition` | groundwater_type、aquifer、recharge_discharge | 相对稳定的水文地质背景 |
| `GroundwaterObservation` | observed_at、level、quality、location | 地下水时序观测 |
| `WaterBody` | type、name、geometry | 河流、沟谷、水库等 |
| `ClimateProfile` | annual_precipitation、annual_temperature、freeze_zone | 区域多年气候背景 |
| `RainfallEvent` | start_time、end_time、cumulative、max_hourly | 降雨过程 |
| `TemperatureObservation` | observed_at、value | 气温观测 |
| `FreezeThawObservation` | observed_at、frozen_depth、cycle_count | 冻融状态 |
| `SeismicContext` | intensity、pga、characteristic_period | 区域地震参数 |
| `VegetationSurvey` | observed_at、type、coverage | 植被调查 |

区域多年平均值不能替代某次暴雨或当前地下水位。风险研判时必须明确使用的是背景数据还是事件数据。

### 8.4 变形、病害和灾害

| 节点类型 | 关键属性 | 说明 |
| --- | --- | --- |
| `HazardBody` | type、geometry、volume、status | 危岩体、潜在滑体、堆积体等 |
| `HazardEvent` | occurred_at、type、scale、loss、description | 已发生灾害事件 |
| `CausalFactor` | type、description、scope | 风化、降雨、坡脚开挖、地震等影响因素 |
| `HazardSusceptibilityAssessment` | hazard_type、level、method、assessment_time | 某时点针对某类灾害的易发性或倾向性评价 |
| `CrackObservation` | observed_at、location、width、length、orientation、filling、persistence | 裂缝观测 |
| `CollapseObservation` | observed_at、location、volume、extent | 滑塌或局部垮塌 |
| `UpliftObservation` | observed_at、location、scale、nature、relative_position | 隆起；规模、性质和相对位置采用反馈版枚举 |
| `SeepageObservation` | observed_at、location、scale、turbidity | 管涌、渗水不再区分现象类型；浑浊程度枚举待确认 |
| `FacilityDamageObservation` | observed_at、location、facility、severity | `facility` 引用受损防护设施，不能将开裂、倾斜等损毁形态误作设施类型 |

变形记录建议采用统一父类或统一字段协议，便于 Agent 按时间查询和计算变化趋势。

### 8.5 防护、排水和养护

| 节点类型 | 关键属性 | 说明 |
| --- | --- | --- |
| `ProtectionWork` | category、subtype、location、design_parameters、completed_at、condition | 大类暂为坡面防护、沿河防护、支挡设施；具体子类后续扩展 |
| `DrainageFacility` | facility_type、dimensions、capacity、condition | 边沟、截水沟、排水沟、急流槽、排水孔等 |
| `MaintenanceEvent` | performed_at、content、result、organization | 养护、维修、加固和清危事件 |
| `InspectionRecord` | inspected_at、scope、condition_grade、inspector | 巡检或定期检查记录 |

防护设施必须表达“类型、设计能力、当前状态”三个层面。仅知道“有主动防护网”不足以证明其仍然有效。

### 8.6 监测

| 节点类型 | 关键属性 | 说明 |
| --- | --- | --- |
| `MonitoringProgram` | name、start_time、status | 监测方案 |
| `MonitoringPoint` | code、location、geometry | 监测点 |
| `MonitoringDevice` | type、model、accuracy、status | 设备 |
| `MonitoringObservation` | metric、value、unit、observed_at、quality | 位移、裂缝、水位、孔压等观测值 |
| `MonitoringAlert` | level、triggered_at、rule_id、status | 监测告警 |

监测数据文件可以保存在文件或时序数据库中，但图谱中至少保留监测点、指标、时间范围、摘要、异常和数据链接。

### 8.7 分析、评定和风险

| 节点类型 | 关键属性 | 说明 |
| --- | --- | --- |
| `AnalysisScenario` | type、rainfall、seismic_load、water_level | 天然、暴雨、地震、治理后等工况 |
| `StabilityAnalysis` | method、safety_factor、required_factor、status、analysis_time | 稳定性计算或分析 |
| `TechnicalConditionAssessment` | grade、assessment_time、method | 技术状况评定 |
| `ExposureObject` | type、importance、people、traffic、distance | 道路、车辆、居民、学校、桥梁、管线等受威胁对象 |
| `ConsequenceAssessment` | level、expected_loss、traffic_impact | 后果评价 |
| `RiskAssessment` | hazard_type、scenario、likelihood、consequence、risk_level、confidence | 风险研判结果 |

风险不能只看失稳可能性，还应考虑暴露、脆弱性和后果。以下表达用于说明组成关系，不代表已经确定具体算法：

```text
风险 = f（危险性或发生可能性，暴露程度，脆弱性，后果严重性）
```

技术状况等级、稳定状态、监测告警等级和综合风险等级应分别保存，不能共用一个“等级”字段。

### 8.8 文档、规则和证据

| 节点类型 | 关键属性 | 说明 |
| --- | --- | --- |
| `Document` | title、file_hash、document_type、version | 勘察、设计、巡检、规范等文档 |
| `PageOrBlock` | page、bbox、text、asset_ref | 页、文本块、表格行或图纸区域 |
| `Drawing` | drawing_no、name、scale、purpose | 平面图、断面图、设计图等 |
| `ImageEvidence` | captured_at、location、file_ref | 现场照片和遥感影像 |
| `Standard` | code、name、version、effective_date | 规范标准 |
| `StandardClause` | clause_no、text、scope | 规范条文 |
| `RiskRule` | rule_id、inputs、expression、output、version | 经专家确认的风险规则 |
| `PropertyAssertion` | subject、property、value、source、valid_time | 属性级证据与冲突管理 |
| `RelationshipAssertion` | subject、predicate、object、source、valid_time | 风险关键关系的证据、置信度与冲突管理 |

## 9. 关系体系

关系必须使用明确、可查询的工程语义，避免大量使用泛化的 `HAS_ATTRIBUTE`、`CONTAINS` 和 `RELATED_TO`。

### 9.1 组织与空间关系

```text
Project           -HAS_ROUTE_SEGMENT-> RouteSegment
RouteSegment      -HAS_SLOPE-> Slope
Slope             -LOCATED_IN-> AdministrativeArea
Slope             -MAINTAINED_BY-> Organization
Slope             -ADJACENT_TO-> WaterBody
```

### 9.2 地质关系

```text
Slope             -HAS_GEOMORPHOLOGY-> Geomorphology
Slope             -HAS_STRATUM-> Stratum
Slope             -HAS_LITHOLOGY-> Lithology
Slope             -CLASSIFIED_AS-> EngineeringGeologicalGroup
Slope             -DEVELOPS-> StructuralPlane
StructuralPlane   -CUTS-> Lithology
StructuralPlane   -CONTROLS-> FailureMode
RockSoilParameterSet -APPLIES_TO-> Lithology
```

### 9.3 灾害与变形关系

```text
Slope             -CONTAINS_HAZARD_BODY-> HazardBody
Slope             -HAS_SUSCEPTIBILITY_ASSESSMENT-> HazardSusceptibilityAssessment
HazardSusceptibilityAssessment -FOR_HAZARD_TYPE-> HazardType
HazardEvent       -OCCURRED_ON-> Slope
HazardEvent       -INVOLVED-> HazardBody
CrackObservation  -OBSERVED_ON-> Slope/HazardBody
RainfallEvent     -TRIGGERED_OR_INFLUENCED-> HazardEvent
DeformationObservation -INDICATES-> FailureMode
```

`TRIGGERED` 需要较强证据。只有相关性而没有充分因果证据时，应使用 `INFLUENCED_BY` 或 `ASSOCIATED_WITH`，并记录置信度，避免把推测写成确定事实。`SUSCEPTIBLE_TO` 可以作为查询展示时的派生关系，但正式事实应来自有时间、方法和证据的 `HazardSusceptibilityAssessment`。

### 9.4 防护和养护关系

```text
Slope             -PROTECTED_BY-> ProtectionWork
Slope             -DRAINED_BY-> DrainageFacility
ProtectionWork    -MITIGATES-> HazardType/FailureMode
FacilityDamageObservation -AFFECTS-> ProtectionWork
MaintenanceEvent  -REPAIRS-> ProtectionWork
MaintenanceEvent  -RESPONDS_TO-> HazardEvent/InspectionRecord
```

### 9.5 监测和分析关系

```text
MonitoringProgram -MONITORS-> Slope/HazardBody
MonitoringPoint   -INSTALLED_ON-> Slope/HazardBody/ProtectionWork
MonitoringObservation -OBSERVED_AT-> MonitoringPoint
StabilityAnalysis -ANALYZES-> Slope/HazardBody
StabilityAnalysis -UNDER_SCENARIO-> AnalysisScenario
StabilityAnalysis -USES_PARAMETERS-> RockSoilParameterSet
StabilityAnalysis -EVALUATES-> FailureMode
StabilityAnalysis -ASSESSED_BY-> StandardClause
```

### 9.6 风险和证据关系

```text
RiskAssessment    -ASSESSES-> Slope
RiskAssessment    -FOR_HAZARD_TYPE-> HazardType
RiskAssessment    -UNDER_SCENARIO-> AnalysisScenario
RiskAssessment    -BASED_ON-> Observation/Analysis/InspectionRecord
RiskAssessment    -APPLIES_RULE-> RiskRule
RiskAssessment    -HAS_CONSEQUENCE-> ConsequenceAssessment
RiskAssessment    -THREATENS-> ExposureObject
Entity             -SUPPORTED_BY-> PageOrBlock/Drawing/ImageEvidence
PropertyAssertion -SUPPORTED_BY-> PageOrBlock/Drawing/ImageEvidence
RelationshipAssertion -SUPPORTED_BY-> PageOrBlock/Drawing/ImageEvidence
RiskRule          -DERIVED_FROM-> StandardClause/ExpertRuleSet
```

## 10. 数据质量、证据和冲突处理

### 10.1 风险关键数据的最小元数据

所有参与风险判断的数据至少应包含：

```text
source_type
source_document_id
source_page_or_record
observed_at / valid_time
extraction_method
confidence
review_status
reviewed_by
version
```

### 10.2 原始抽取结果不能直接发布

建议采用：

```text
原始文件
  -> 解析 Sidecar
  -> 候选实体、属性和关系
  -> 实体归一与冲突检测
  -> 人工或规则审核
  -> 已发布知识图谱
```

LLM、OCR、表格抽取产生的是候选知识，不应默认等同于已审核事实。

### 10.3 多来源冲突

当勘察报告、施工图、巡检记录出现不同数值时，不应直接覆盖。应保留多条 `PropertyAssertion`，并根据以下原则确定当前有效值：

1. 时间较新的有效调查优先于旧资料。
2. 实测数据优先于概述性描述。
3. 已审核数据优先于自动抽取候选。
4. 同等条件下按来源权威级别处理。
5. 冲突无法消解时标记 `conflicted` 并进入人工复核。

### 10.4 单位和枚举

- 所有数值必须有标准单位。
- 原始文本应保留，标准值用于计算。
- 枚举必须有稳定代码，不以中文展示名作为唯一主键。
- 坡度应同时保留原始表达和统一换算值。
- 桩号应同时保留原始字符串和标准累计里程。

## 11. 风险研判 Agent 设计

### 11.1 职责边界

风险 Agent 的职责是：

1. 确定目标边坡、评估时点和评估场景。
2. 查询图谱中的有效事实和最新记录。
3. 检查风险关键字段是否缺失或过期。
4. 识别可能的灾害类型和破坏模式。
5. 调用已审核的规则、评分模型或专业计算模型。
6. 综合防护有效性、暴露对象和后果。
7. 生成带依据、带置信度、可人工复核的风险评估。

Agent 不负责：

- 自行发明工程阈值；
- 将未知值当作无风险；
- 用语言模型替代稳定性计算；
- 无证据地确定因果关系；
- 自动发布未经审核的高风险处置指令。

### 11.2 推荐技术结构

```text
知识图谱：事实、关系、时间、来源、规则索引
时序/监测存储：高频监测和气象数据
规则引擎：确定性阈值、评分表、专家规则
专业模型：稳定性、位移趋势、降雨阈值等计算
LLM Agent：任务编排、查询生成、信息归纳和可解释报告
人工审核：规则发布、风险结论确认和处置决策
```

风险规则可以作为 `RiskRule` 节点登记输入、输出、版本和规范来源，但规则表达式应由可审计的规则引擎执行，不能只以自然语言保存在图谱中。

### 11.3 Agent 工作流程

#### 第一步：对象和场景确认

```text
目标：G209-S08
时点：2026-07-10
场景：当前状态 / 连续降雨 / 地震 / 治理后
```

#### 第二步：数据完整性检查

至少检查：

- 基础几何；
- 岩土分类和岩性；
- 结构面和潜在破坏模式；
- 最新变形巡检；
- 最新降雨和地下水信息；
- 防护及排水设施状态；
- 有效稳定性分析；
- 灾害历史；
- 暴露对象和交通影响；
- 所用数据的证据与审核状态。

如果关键数据不足，应先输出“数据不足”和补采建议，而不是强行输出确定等级。

#### 第三步：灾害模式识别

以下仅为规则形态示例，最终条件和阈值须由交通部研究院结合相关专业要求确认：

```text
高陡岩质边坡
+ 外倾或不利结构面
+ 节理裂隙发育
+ 历史落石
=> 崩塌/落石可能性提高
```

```text
覆盖层较厚
+ 坡顶裂缝或局部滑塌
+ 连续降雨
+ 地下水位上升
=> 滑坡可能性提高
```

#### 第四步：稳定性和规则判断

```text
选择与评估场景一致的稳定性分析
-> 检查参数和分析时间是否有效
-> 根据工程等级选择规范阈值
-> 比较实际安全系数和要求安全系数
-> 结合监测趋势和防护设施状态修正判断
```

#### 第五步：后果和综合风险

综合道路等级、交通量、断通影响、人员、居民点、桥梁、学校和其他重要设施，形成后果等级，再与发生可能性组合得到风险等级。

#### 第六步：形成风险评估记录

每次评估都生成新的 `RiskAssessment`，不覆盖边坡历史：

```json
{
  "assessment_id": "ra-20260710-g209-s08-rainfall",
  "assessment_time": "2026-07-10T20:00:00+08:00",
  "slope_id": "g209-s08",
  "scenario": "continuous_rainfall",
  "hazard_type": "landslide",
  "likelihood_level": "high",
  "consequence_level": "medium",
  "risk_level": "high",
  "confidence": 0.78,
  "missing_critical_data": ["recent_groundwater_level"],
  "triggered_rule_ids": ["RULE-LS-003", "RULE-DR-002"],
  "review_status": "pending"
}
```

### 11.4 Agent 输出要求

风险报告至少包含：

1. 评估对象、时间和场景；
2. 风险类型和等级；
3. 主要风险因子；
4. 使用的数据及有效期；
5. 触发的规则和规范依据；
6. 防护设施有效性；
7. 暴露对象和可能后果；
8. 缺失或冲突的数据；
9. 置信度；
10. 建议的复核、监测或处置措施；
11. 人工审核状态。

## 12. G209 示例资料映射

### 12.1 现有13个“灾害点”的处理

现有 Demo 中13个 `HazardPoint` 不应直接、无条件地全部改名为 `Slope`。建议按以下流程迁移：

1. 根据路线、起止桩号、侧别建立13个候选 `Slope`。
2. 核查每个候选范围是否对应独立可管养边坡。
3. 将危岩体、潜在滑体等建立为 `HazardBody`。
4. 将“崩塌落石、危岩体”等拆分为灾害类型、灾害体和历史记录。
5. 将“不稳定边坡”转换为稳定性状态或评估结论，而不是与崩塌、滑坡完全同类的标签。
6. 保留原灾害点名称作为 `source_alias`，避免丢失原文表达。

在交通部研究院确认前，可设置：

```text
entity_resolution_status = provisional
```

### 12.2 K2412+602～K2412+664 示例

可按以下方式组织：

```text
Slope: G209-S08
  基础属性：
    route = G209
    start_station = K2412+602
    end_station = K2412+664
    side = 右侧
    length_m = 62
    road_grade = 二级公路（正式归属于 RouteSegment）

  关系：
    BELONGS_TO -> G209路线段
    CONTAINS_HAZARD_BODY -> 潜在不稳定坡体
    HAS_DEFORMATION -> 坡顶小范围垮塌记录
    HAS_DEFORMATION -> 降雨期间表层堆积体溜滑记录
    AFFECTED_BY -> 风化作用
    DEVELOPS -> 节理裂隙
    SUSCEPTIBLE_TO -> 滑坡/崩塌落石
    HAS_ANALYSIS -> 天然工况稳定性分析
    HAS_ANALYSIS -> 暴雨工况稳定性分析
    PROTECTED_BY -> 具体防护工程实例
    SHOWN_IN -> SDZ-X08系列施工图
    SUPPORTED_BY -> 勘察报告和施工图对应页
```

### 12.3 两份 PDF 的可覆盖内容

| 数据项 | 当前 PDF 覆盖情况 |
| --- | --- |
| 路线、桩号、侧别、长度 | 较好 |
| 部分坐标、高程、坐标系 | 较好 |
| 公路等级、区域位置 | 较好 |
| 灾害类型、危岩体和不稳定边坡描述 | 较好，但需概念拆分 |
| 地形地貌、地层岩性、结构面 | 可抽取，细粒度需继续核查 |
| 区域气候、水文和地震参数 | 有背景资料 |
| 变形机理、致灾因素 | 有文本描述，需要结构化和审核 |
| 稳定性工况、方法、参数和结果 | 有较强基础 |
| 防护方案、设计参数、图纸和工程数量 | 有较强基础 |
| 实际养护历史和当前设施状态 | 不足 |
| 当前裂缝、位移和地下水趋势 | 不足 |
| 实时降雨和气温 | 不足 |
| 当前交通量和受威胁对象 | 不足 |

因此，G209 PDF 可以构建历史基线和设计状态，但不能单独支撑当前实时风险判断。

## 13. 对现有属性数据字典的调整建议

### 13.1 增加字段重要性分级

当前数据字典大部分字段均为 `required=false`，无法指导验收。建议增加：

```text
core_required          建立边坡档案必须具备
risk_required          进行某类风险研判必须具备
conditional_required   满足条件后必须具备
optional               可选补充
```

不同灾害类型可以具有不同的 `risk_required` 字段集合。

### 13.2 将复合字段升级为独立记录

以下字段应从单个 JSON object 调整为可重复记录模型：

- `disaster_history` -> `HazardEvent[]`
- `maintenance_history` -> `MaintenanceEvent[]`
- `cracks.items` -> `CrackObservation[]`
- `collapses.items` -> `CollapseObservation[]`
- `uplifts.items` -> `UpliftObservation[]`
- `piping_or_seepage.items` -> `SeepageObservation[]`
- `facility_damages.items` -> `FacilityDamageObservation[]`

### 13.3 新增当前缺失的数据域

至少补充：

- 坡向、坡形和台阶信息；
- 地层、岩性、风化和结构面；
- 岩土物理力学参数；
- 地下水和地表水观测；
- 降雨、气温、冻融和地震场景；
- 稳定性分析；
- 防护设施状态和有效性；
- 暴露对象和后果；
- 风险评估；
- 属性级证据与审核信息。

### 13.4 需要交通部研究院确认的原字段

1. `road_slope_relation` 中“上行/下行”的确切业务含义。
2. `slope_length_m` 是沿路线长度、坡面长度还是水平投影长度。
3. 是否正式记录边坡所在左岸/右岸。
4. 三类防护设施下的具体子类型。
5. 管涌、渗水的浑浊程度枚举。
6. 单处设施损毁严重程度枚举。
7. 监测位置与监测数据接入后的引用方式和接口结构。
8. 技术状况1～5类所依据的具体标准和判定流程。
9. “高边坡”属性表是否仅覆盖高边坡，普通边坡是否采用同一 Schema。

## 14. 逻辑存储与展示建议

### 14.1 逻辑存储

建议按数据特点分层，而不是要求所有数据都放进同一种数据库：

```text
文件存储：PDF、图纸、照片、遥感影像、监测原始文件
结构化存储：边坡主档、字段字典、证据断言、审核和版本
图数据库：实体、事件、分析、规则和语义关系
时序数据库：高频监测、降雨、水位和温度
空间数据库：边坡范围、监测点、水系和暴露对象
向量索引：文档块、图纸说明和实体描述的语义检索
```

MVP 阶段仍可使用 JSONL、SQLite/DuckDB 和 GraphML；后续再根据查询量接入 Neo4j/NebulaGraph、PostGIS 和时序数据库。逻辑 Schema 不应绑定某一具体数据库产品。

### 14.2 前端展示

底层图谱不等于前端必须一次性展示所有节点。建议提供多种视图：

- 边坡档案视图：像属性表一样查看基本信息；
- 地质结构视图：地层、岩性、结构面和破坏模式；
- 灾害演化视图：变形、灾害、养护和风险时间线；
- 防护设施视图：工程设施、状态、损毁和维修；
- 风险证据视图：风险因子、规则、分析结果和来源证据；
- 全量图谱视图：用于专业查询和调试。

现有 HTML 演示中的树形形式可以保留为“边坡档案视图”，但不应直接作为底层图谱 Schema。

## 15. 分阶段实施建议

### 第一阶段：Schema 和基线图谱

1. 确认边坡、灾害体、灾害事件和稳定性状态的概念边界。
2. 确认边坡核心属性、枚举、单位和必填级别。
3. 将 G209 的13个灾害点迁移为候选边坡及关联灾害体。
4. 抽取桩号、坐标、岩性、结构面、稳定性、防护和图纸。
5. 建立文档页级及关键属性级证据。
6. 形成可查询、可回链、可审核的基线图谱。

### 第二阶段：巡检、养护和动态记录

1. 接入裂缝、滑塌、渗水和设施损毁记录。
2. 建立防护设施实例及状态。
3. 接入养护历史和处置效果。
4. 建立时间线和版本管理。

### 第三阶段：风险规则和 Agent 原型

1. 由专业人员确认灾害模式和风险指标。
2. 将规范阈值和专家规则登记为可版本化规则。
3. 实现数据完整性检查和场景选择。
4. 实现规则调用、稳定性结果比较和可解释报告。
5. 所有结论保持待审核状态，经过人工确认后发布。

### 第四阶段：监测和动态风险

1. 接入降雨、位移、裂缝、地下水和设备数据。
2. 增加趋势分析和动态阈值。
3. 增加监测告警、风险更新和闭环处置。
4. 逐步积累可用于模型训练的高质量历史样本。

## 16. 验收建议

### 16.1 Schema 验收

- 节点和关系定义清晰，不以“相关”代替专业语义。
- 边坡、灾害体、灾害事件、状态和风险评估边界明确。
- 字段具有类型、单位、枚举、必填级别和时间属性。
- 未知、缺失、不适用和确认不存在能够区分。

### 16.2 数据验收

- 每个边坡具有稳定 ID 和标准化空间位置。
- 风险关键字段具有来源和审核状态。
- 动态记录保留历史，不覆盖旧值。
- 多来源冲突可发现、可追踪、可复核。
- 自动抽取结果与已审核事实明确区分。

### 16.3 图谱验收

- 不仅能展示边坡属性，还能查询地质、灾害、防护、监测、分析和证据之间的路径。
- 同类岩性、结构面、措施和规范可以跨边坡关联。
- 可以从风险结论回溯到规则、分析结果、观测记录和原始资料。
- 可以按时点重建某边坡当时的数据状态。

### 16.4 Agent 验收

- 能识别关键数据缺失并拒绝无依据的确定判断。
- 能针对不同灾害类型和场景选择相应数据与规则。
- 输出包含风险因子、规范依据、数据来源、缺失项和置信度。
- 风险评估生成独立版本，不能覆盖历史。
- 相同输入、相同规则版本应得到可复现结果。
- 高风险结论和处置建议必须进入人工审核流程。

## 17. 待讨论的关键问题

后续方案评审中，建议优先确认以下问题：

1. 一处“边坡”的业务划分标准是什么，是否以管养单元、桩号区间或地质单元为准？
2. 当前13个灾害点是否可以一一对应13个边坡，还是一个边坡可能包含多个灾害点？
3. 风险 Agent 首期针对哪些风险：崩塌、滑坡、落石、泥石流，还是综合风险？
4. 风险等级采用哪套标准，是否已有现行风险评分标准？
5. 哪些字段是风险研判的强制输入，缺少哪些字段时必须停止判断？
6. 是否能够提供巡检、养护、监测、交通量和历史灾害样本？
7. Agent 输出是辅助研判、预警建议，还是直接进入业务处置流程？
8. 风险结论由谁审核、谁发布、有效期多长？

## 18. 总结

本项目的底层图谱不应做成“边坡—属性类别—属性值”的普通树，也不应为了追溯来源而把所有数值都暴露成业务节点。较合理的结构是：

```text
边坡稳定属性
+ 领域实体关系
+ 时间事件与观测
+ 稳定性及风险分析
+ 规范规则
+ 证据断言与审核
```

边坡作为核心实体负责回答“对象是谁、在哪里、基本形态是什么”；地质、灾害、防护、监测和分析子图负责回答“为什么可能失稳、发生过什么、当前发生了什么、已有措施是否有效”；规范和风险规则负责回答“应如何判断”；证据层负责回答“判断依据来自哪里”。

在这一结构上建设的 Agent 才能从简单的资料问答进一步发展为可计算、可解释、可追溯、可审核的风险研判辅助系统。
